# MDedit v0.3.15

## Editor responsiveness and rendering

- Markdown parsing, footnote expansion, math preparation, syntax highlighting, regex searches, and large recovery snapshot encoding/write-validation parsing run in workers.
- Regex searches have a 500 ms deadline and searches stop at 10,000 matches rather than exposing partial replacements. Rapid asynchronous replacement requests are serialized safely.
- Native document and recovery filesystem operations run on blocking tasks instead of the WebView dispatch thread.
- Preview and export worker results retain document/revision ownership; optional highlighting failures leave code plain. Sanitization and DOM-dependent rendering remain on the UI thread.

## Recovery and correctness

- Browser recovery retains the draft referenced by the selected valid manifest across repeated unpublished writes and restarts, including quota and corruption fallback cases.
- Recovery encoding failures remain visible until explicit retry succeeds. Restore-on-quit waits for checkpoint completion.
- Recovery, preview, and ordinary operation status are independent: successful previews or exports cannot hide a recovery failure.
- Fixed cached Markdown-link navigation races and avoided unnecessary large textarea reads during workspace restoration and empty Find refreshes.

## Security, documentation and verification

- Enabled desktop Content Security Policy and documented the privileged frontend's remaining filesystem trust boundary in `docs/security.md`.
- Added generated-file verification, Linux release-WebView automation, and worker, recovery, rendering and security regressions.
- Refreshed README branding and screenshots.
- The pre-release implementation passed main-branch browser tests, native-core tests and desktop builds on Linux, macOS and Windows, including the real Linux WebView smoke test. The smoke test now targets the selected tab's managed editor rather than the hidden bootstrap textarea.

## Known limits

- The existing 250 MiB activation benchmark fails in the documented local Windows/Chromium environment, including on the unchanged baseline. No performance budget was relaxed; this release does not claim that large-session latency target is met. Tag-triggered performance verification remains a release gate.
- Browser recovery is not a cross-window transaction, version-history store or power-loss durability guarantee. Custom native filesystem commands still trust the application frontend; per-file authorization tokens are not introduced.
- Small snapshots, recovery-read parsing, manifest handling, storage commits, sanitization, DOM insertion, KaTeX and Mermaid DOM rendering still run on the UI thread.
- Desktop downloads remain unsigned.
