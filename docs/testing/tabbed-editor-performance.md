# Tabbed editor performance evidence

The release workload is 50 restored documents with 5 MiB of Markdown content each (250 MiB total), followed by 200 loaded-tab activations. The reference browser environment is a GitHub-hosted `ubuntu-latest` x64 runner with Node.js 20 and headless Playwright Chromium. Release budgets are p95 tab activation at or below 100 ms and peak observed main-page JavaScript heap at or below 1 GiB. The 1 GiB ceiling leaves deliberate headroom over the approximately 435 MB observed baseline while still catching large regressions.

`npm run test:performance` writes `test-results/tab-activation-metrics.json`. This is browser fake-bridge evidence: it measures real DOM/editor activation and the page's observed heap. `performance.memory` does not account for worker-isolate heaps or native allocations; moving parsing to a worker must not be presented as reducing total application memory on the basis of this metric alone. The existing 1 GiB assertion is unchanged. The fake recovery invoke timing does not include native IPC or disk I/O. It must not be presented as native recovery evidence.

The ignored Rust `recovery_performance` diagnostic serializes a real 5 MiB recovery snapshot and passes it through `RecoveryStore::write_document`, including validation and the atomic disk write. The manual/tag-only performance CI job runs it in release mode and writes `test-results/native-recovery-metrics.json`. Its artifact reports durations without enforcing an unapproved storage-latency threshold. It does not include webview IPC.

Before release, run the packaged smoke checklist on Windows, macOS, and Linux and record an end-to-end 5 MiB checkpoint measurement from `window.__MDEDIT_RECOVERY_PERFORMANCE__`. Each bounded entry contains snapshot encoding, IPC-plus-native, native atomic-write, and combined component durations. `serializationMode` distinguishes `synchronous-duration` from `asynchronous-latency`; the latter includes cold startup when applicable, encoder queueing and worker request/response transfer, not just worker CPU time. Production prewarms the worker via a readiness handshake before bulk restoration to avoid cold startup competing with expensive textarea layout. `endToEndDurationMs` remains the sum of the reported encoding and IPC/native components; it is not an independent wall-clock measurement of every checkpoint queue. Large snapshot encoding uses a single worker when estimated string fields total at least 256 Ki UTF-16 code units. Small DTOs/manifests remain synchronous. Browser write validation now parses large incoming/current JSON in that same queued worker (raw JSON length at least 256 Ki UTF-16 code units); bounded schema checks, recovery reads, localStorage commits and Tauri IPC argument construction remain on the UI thread. These packaged measurements remain a manual release gate because the automated Rust diagnostic cannot honestly measure webview serialization and IPC across all three desktop runtimes.

`test-results/recovery-validation-metrics.json` separately compares an explicitly injected synchronous parser against worker parsing for two 5 MiB browser-adapter writes. The baseline parses incoming JSON twice and the current copy once; the worker path forbids these large main-thread parses. It uses in-memory storage to isolate validation from localStorage quotas, measures queue/transfer plus metadata-check latency, and does not measure native IPC/disk I/O, total application memory, or the unchanged 250 MiB activation budget. This is a controlled parser-policy comparison, not a historical whole-application performance baseline.

`test-results/syntax-highlighting-metrics.json` compares the vendored direct Highlight.js API against a cold highlighting worker for the same JavaScript block. Markup must match while parent-thread highlighting is forbidden during the worker request. Direct-engine duration and worker elapsed time are different measures: the latter includes startup, processing and transfer, while neither measures the complete preview's sanitization/DOM insertion, native I/O or total worker/process memory. This diagnostic does not replace or relax the large-session activation budget.
